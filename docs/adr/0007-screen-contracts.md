# 7. Screen contracts

Status: accepted and built (epic #162). `examples/mvd-colours.cuppa` is the design of MVD's Colours screen, checked by a test.

## Context

Cuppa exports a design as a whole Go program. That suits a new app, not one that already exists: a program like MVD owns its state and logic and only wants its *views* to come from a design. Reading hand-written Go back into a design (import, or a live connection that rewrites source) was considered and dropped: the layout of such code is procedural (strings joined and padded), so there is no rectangle in the source to change.

The direction is the other way round: the design is the source of truth, the program calls what Cuppa generated, and the generated code is never edited by hand.

## Decision

### A screen is a design, exported as a contract

Each `.cuppa` design is one **screen**. The *screens* export writes, per design, into a package of its own:

| File | Holds |
|---|---|
| `<screen>_screen_contract.go` | `<Screen>Props` (the inputs), `Default<Screen>Props()`, the `<Screen>Event` interface with one struct per event, `<Screen>Keys` |
| `<screen>_screen_view.go` | the placed components, `<Screen>(props, w, h) Frame`, `<Screen>Size()`, `<Screen>Handle(frame, msg) (event, ok)` |
| `cuppa_runtime.go`, `cuppa_widgets.go`, `cuppa_screens.go`, `cuppa_<ext>.go` | the shared drawing code (the same runtime as the program export) and `Frame`, `Region`, `Theme`, `KeyHint` |

Every file starts with `// Code generated by Cuppa. DO NOT EDIT.` Cuppa replaces files that start with it and refuses to touch any other file in the folder.

### Bound properties

A property of a component can be **bound** to a named input (`bind`: property key to input name). The value stored in the design stays as the input's default and as what the design shows. The Go type comes from the property:

| Property | Go type |
|---|---|
| number | `int` |
| yes/no | `bool` |
| text, colour, choice | `string` |
| list text (`items`, `options`, `entries`, `tabs`, `buttons`, `columns`, `labels`, `headers`, `bindings`, `checked`, `values`) | `[]string` |
| table `rows` | `[][]string` |

The same input name may be used by several components when the type is the same; a clash is reported in the export notes and the second use stays as designed.

### Visibility

`showIf` names a yes/no input; the component is drawn only while it is true. The input is a `bool` field of the props.

### Events are returned data, not callbacks

A component's `event` names what a click on it raises, and the design's `keys` (`key=Event:label`) raise events from the keyboard. `<Screen>Handle(frame, msg)` turns a Bubble Tea click or key into a typed event (`ColoursSave{X, Y}`: the cell inside the component, 0 for a key) and the program switches on it.

Callbacks were rejected: Bubble Tea models are values, so a closure that sets a field changes a copy. A returned event can be tested without a terminal.

### Theme

The design's theme roles (text, muted, border, secondary and the background) are the **theme tokens**. A colour a component has not set follows its role; the screen takes a `Theme` in its props, and an empty value keeps the design's own colour. A colour that must differ per screen state is a bound colour property.

### Regions

`Frame.Regions` lists the visible components with their rectangle, back to front. The program can place something over a component (`Frame.RegionNamed`) or hit-test itself. A click is resolved to the topmost region that raises an event.

### Responsive

Layout expressions (ADR 0006) are followed against the `w` and `h` the program passes, so a screen fills whatever area it is given.

### One design per screen, folder export

`cuppa screens <design.cuppa|folder>... -o <folder> [-p package]` exports many designs at once and removes the generated files of a design that is gone. The Export menu's *Go screen (contract)…* writes the open design into a folder and leaves other screens in it alone.

### Versioning

The contract is the Go types. A removed or renamed input or event is a compile error in the program, which is the point. The file format stays at version 1: `bind`, `showIf`, `event` and `keys` are optional.

## Limits of this first version

- A bound text input is a `string`; the exported component draws a static cursor. Stateful Bubbles models (a `textinput.Model` the program owns) are not passed in yet.
- Lists are joined with commas and rows with semicolons, so an item cannot hold a comma.
- There are no per-row events or row templates: a click event carries the cell, from which a program derives the row.
- Bindings, show-if and events on a group or a pack component are not exported (a note says so); set them on the parts.
- The runtime is copied into the package, so each screens package carries its own copy.

## Not in this decision

- Reading Go source back into a design, and a live connection to a running program. Both were replaced by this direction.
- Row templates and other data-driven components.
